# Word の PDF は 0.57% 太い

クローズドなレイアウトエンジンを再現するには、それを測るしかない。Word には都合よく二つの窓がある。COM は構造の、PDF に書き出した結果は最終描画のオラクルになる。ところがこの PDF は、素直に読むと系統的に嘘をつく。セル幅を 1 twip 刻みで振った 14 腕 × 502 セル = 7028 サンプルの掃引で、そのうち五つが同時に姿を現した。どれも「もっともらしく間違った表」を作れるものばかりだった。

## 測り方

掃引用の docx をプログラムで生成し、Word COM の `ExportAsFixedFormat(path, 17)` で PDF にし、PyMuPDF の `rawdict` から文字ごとの bbox を読む。送りは必ず隣接文字の原点差で取る。

```python
adv = [chars[i+1]["bbox"][0] - chars[i]["bbox"][0] for i in range(len(chars)-1)]
```

行 bbox の `x1 - x0` を字数で割ってはいけない。最後のグリフのインクは送り箱の外へはみ出すので、それは送りではない。

## 1. フォントサイズは 1/600 インチにスナップされる

`w:sz w:val="21"`（10.5pt）と書いた文書を Word が PDF に出すと、スパンのサイズは **10.56** で返ってくる。8pt は **8.04**、10pt は **9.96**。

```text
size_pdf = round(pt × 600 / 72) × 72 / 600

10.5pt → round(87.50) = 88 → 88 × 72/600 = 10.56
 8.0pt → round(66.67) = 67 → 67 × 72/600 =  8.04
10.0pt → round(83.33) = 83 → 83 × 72/600 =  9.96
```

600 dpi はプリンタの解像度である。Word はサイズをデバイス単位へ丸めてから書き出している。

これが厄介なのは、**比では消える**からだ。送りを `span["size"]` で割って em 単位で扱っている限り影響はゼロで、フォントメトリクスの導出はこの罠を踏まずに何年でも進む。絶対値を pt で読んだときにだけ、すべての送りが 0.57% 太る。

> **測るときは** 送りは常に span size で割る。PDF から絶対 pt を持ち出さない。

## 2. 折り返しに使う幅は、描いている幅ではない

前項の 10.56 を「Word の実際の送り」だと思うと、次に詰む。

セル幅を 1 twip ずつ振った 502 個の一列表を作り、どのセルにも同じ全角ランを左揃えで入れる。左揃えなので Word は行を伸ばさない。1 行目の字数が k から k+1 に変わる幅が、そのセルの折り返し予算を twip 単位で刺す。

k 字入る条件を `k·a + C ≤ w < (k+1)·a + C` と書けば、502 個のセルが 502 組の不等式をくれる。送り a と定数 C は点ではなく**領域**として解ける。

答えは **a ∈ [10.495, 10.505]**。指定どおりの 10.500 だった。そして描画上の 10.560 は、14 腕すべてで**空区間**として棄却された。どんな C を選んでも 502 個の不等式を同時に満たせない。

Word は公称サイズで折り、スナップ後のサイズで描いている。

> **測るときは** 描画上の送りから折り返し予算を導かない。折る側と描く側は別の数を使っている。

## 3. 掃引窓が一つだと、1 字の幅と定数が分離しない

最初は 0.5pt 格子で一本の窓だけを振った。遷移は 53.00 / 63.50 / 74.00 / 84.50 / 95.00 / 105.50 / 116.00pt に出て、差はすべてきっかり 10.50。`C = w* − (k+1)×10.50` は 7 本すべてで 11.00 に揃った。完璧に見えた。

しかし同じ 7 本は「10.56/字 + 定数 10.3」でも説明がつく。0.5pt 格子の上では、両者は 7 本の範囲でまったく同じ折り位置を予測する。1 字あたり 0.06 の差が積もって格子をまたぐには、もっと長いベースラインが要る。

窓を二つ、離して置いた（50–62.5pt と 112.5–125pt）。6 字ぶん離れた二つの遷移が、0.06 の差を 0.36 に育てて分離してくれる。

> **測るときは** 係数と定数を同時に推定するなら、遠く離れた二点を取る。一窓での「完璧な一致」は、正しさの証拠ではなく縮退の証拠かもしれない。

## 4. PDF テキスト抽出器は空白グリフを捏造する

MuPDF は、隣り合うグリフの隙間が十分に広いと、そこに空白文字を挿入して返す。CJK と欧字の境（Word が入れる和欧間アキ）はそれだけで閾値を超える。

字間設定を 8 段階に振った同じ probe で、`w:spacing` が 0 と −10 の行にだけ `' '` が入った。残り 6 行には入らない。文字位置で索いていた解析表は、その 2 行だけ列が一つずれ、「4 の送り」の欄に和欧間アキの値を出した。値は 2.100 や 7.083 のようにもっともらしく、しかも行ごとに違うので、ノイズにしか見えない。

> **測るときは** 文字単位の解析は位置ではなく**文字で索く**。`ch.index("あ")` であって `adv[4]` ではない。

## 5. Word は整数 twip で計算する — 浮動小数点では「ちょうど」が入らない

セル幅 52.8pt、左右の内側余白が各 5.4pt。内寸は 42.00pt で、10.5pt の全角 4 字がちょうど収まる。Word は整数 twip で計算するので収まる。

```text
1056 twip − 108 − 108 = 840 = 4 × 210     ちょうど
```

f32 の pt では収まらない。

```text
52.8f32 − 5.4f32 − 5.4f32 = 41.99999904
```

4 字目に必要な 42.00 に 1 ulp 足りず、最後の一字が次の行へ落ちる。

これは丸め誤差の小話ではない。和文のフォーム表は列幅を「N 字ちょうど」で決めるので、**ちょうど収まる場合が例外ではなく常態**である。7028 セルの掃引で予測を外したのは 3 セルだけで、その 3 つはすべてこのケースだった。予算を twip 格子へ丸めた瞬間に 7028/7028 になった。

> **測るときは** 比較の前に予算を twip へ丸める。Word の算術は整数である。

## まとめ

| | 素直に読むと | 実測 |
|---|---|---|
| 10.5pt のスパンサイズ | 10.50 | **10.56**（1/600 インチ丸め） |
| 折り返しに使う送り | 描画と同じ 10.56 | **10.500**（公称 em） |
| 一窓の掃引 | 係数も定数も決まる | 縮退していて決まらない |
| 抽出器の返す文字列 | 文書の文字そのもの | 空白が捏造されうる |
| ちょうど収まる幅 | 収まる | f32 では 1 ulp 足りない |

五つのうち四つは、それ単独では小さな誤差にしか見えない。厄介なのは、これらが互いに打ち消し合うことだ。0.57% 太い送りと、少し広すぎる予算は、同じ位置で折れてしまう。だから片方だけを直すと結果は悪化する。掃引して領域として解くというのは、要するに「打ち消し合っている二つを同時に見る」ための手続きだった。
